## 2. 项目背景与目的
**背景：** 
当前在嵌入式设备上部署AI模型时，高度依赖如STM32CubeAI等厂商工具链。这类工具存在严重的平台绑定问题，限制了代码的可移植性，且其黑盒特性阻碍了对底层计算逻辑的深度优化与掌控。
**目的：** 
开发一套独立、轻量级的双组件工具链，剥离“模型解析”与“底层计算”的过程。通过人工介入网络结构的C代码构建，实现完全脱离特定平台依赖、零运行时开销的神经网络推理部署，并借此彻底掌握神经网络底层算子的C语言实现细节。
## 3. 项目范围
### 3.1 包含在范围内
* **软件一：ONNX解析与转换工具（建议基于Python）**
  * 解析指定ONNX模型文件的计算图结构。
  * 提取各层算子类型、参数（如kernel_size, stride等）并输出人类可读的结构清单。
  * 提取模型权重数据，自动转换为C语言头文件（`.h`）中的常量数组。
* **软件二：C语言底层算子库**
  * 使用纯C语言实现基础神经网络算子（初步包含：`conv2d`, `depthwise_conv2d`, `relu`, `linear/gemm`, `max_pool`, `softmax`等）。
  * 算子接口设计为无状态、无动态内存分配，数据指针与参数由外部传入。
* **集成胶水层（人工构建）**
  * 基于软件一的输出，人工编写`model.c`，调用软件二的算子库拼接网络结构。
* **验证与测试**
  * 在PC端搭建交叉验证环境，对比C代码输出与Python (PyTorch/ONNX Runtime) 输出的精度。
### 3.2 不在范围内
* 自动化的图调度与C代码生成引擎（网络结构由人工拼接，不写编译器）。
* 全量ONNX算子集兼容（仅实现目标模型用到的算子）。
* 针对特定芯片的汇编级指令优化（如DSP指令，初期以标准C实现为主）。
* 模型的训练与量化微调流程。
## 4. 项目目标 (SMART原则)
1. **功能目标：** 在项目结束前，成功将至少1个指定的ONNX模型（如简化版MNIST分类网络）通过本工具链转换为C代码，并在PC端跑通端到端推理。
2. **性能目标：** C语言实现的前向推理结果，与Python端ONNX Runtime推理结果相比，单元素绝对误差小于 `1e-4`。
3. **可移植性目标：** 核心C算子库及模型代码不包含任何平台专有头文件（如`windows.h`或`stm32f4xx.h`），可在任意支持标准C99的编译器下直接编译通过。
## 5. 高层级需求
| 编号 | 需求描述 | 优先级 |
| :--- | :--- | :--- |
| REQ-01 | 软件一需支持通过命令行参数指定ONNX文件路径及输出目录。 | 高 |
| REQ-02 | 软件一生成的权重头文件需包含维度信息宏定义，防止人工拼接时越界。 | 高 |
| REQ-03 | 软件二算子函数需明确输入/输出张量的内存布局（统一约定为NCHW或NHWC）。 | 高 |
| REQ-04 | 软件二不得在算子内部使用`malloc`/`free`，所有内存由调用方分配。 | 高 |

## 8. 假设条件与制约因素
* **假设条件：**
  * 目标ONNX模型结构在项目开发期间保持相对稳定，不频繁增删网络层。
  * 开发者具备基本的Python编程能力及熟练的C语言指针与内存管理能力。
* **制约因素：**
  * **人工拼接成本：** 模型结构若极为复杂（如上百层），人工编写`model.c`易出错且耗时。
  * **算子兼容性：** 若ONNX模型中出现了未在软件二中实现的算子，需暂停开发新算子方能继续。
  * **性能瓶颈：** 纯C实现的卷积层可能在算力孱弱的MCU上运行较慢，初期不考虑极致性能优化。
## 9. 高层级风险
| 风险项 | 影响 | 概率 | 应对策略 |
| :--- | :--- | :--- | :--- |
| **人工拼接维度错位** | 高 | 高 | 软件一在结构清单中明确打印每一层的Tensor Shape；在C代码中增加断言检查。 |
| **C指针内存越界** | 高 | 中 | 算子库设计中强制传入缓冲区大小参数；使用Valgrind等工具进行内存检测。 |
| **浮点数精度漂移** | 中 | 中 | 统一PC端C编译器与目标MCU的浮点运算模式（如均使用硬浮点FPU）。 |
